# Stage 1: bounded in-place restore and import safety correction

This is a new material group after the signed-full source/test freeze. Read-only plan review only; no source changes, tests, runtime actions, or staging are authorized by this review. Existing owner request covers production audit/fixes; parent will reconcile approval and sequence.

## Confirmed current behavior

See docs/audits/2026-10-29/evidence/import-restore-failure-trace.md for exact trace.

1. restore.sh interrupted-destructive branch stops runtime, but leaves destructive=0/restart_allowed=1; failed pg_restore/object/journal work enters EXIT and restarts writers. The regular destructive EXIT branch ignores object/journal failures and calls backup_control fail, which unconditionally changes RecoveryState to NORMAL. Root marker remains NORMAL/ACK_NORMAL throughout. SQL may be partial or DB/object state inconsistent.
2. Successful disaster restore sets DB QUARANTINED but starts worker and beat; default TenantGateTask has no global recovery-mode admission, even for outbound email tasks. The host marker still admits every role.
3. Different-key import installs changed .env before stopping current processes. The next Compose wrapper refuses exact environment hash drift, so ordinary import stops BEFORE intent/SQL. Existing containers generally still hold old settings. Do not claim current default path performs SQL under wrong keys. Host .env is nevertheless changed and supported commands cannot continue.
4. Existing task configuration has one default Celery queue, no explicit task_routes/default_queue override, ACKS_LATE, and tasks keyed by integer EmailLog/NotificationDeliveryLog/BulkImportJob IDs. A restored database can reuse an old queued ID. A recovery mode check only prevents work during quarantine; it does not prevent stale target jobs running after acknowledgement.

## Scope and limits

Correct only the actual shipped bundled in-place signed-full/historical same-host path and its signed-full import wrapper. Unsupported compound B1 restores remain refused before config/intent effects. No concrete sovereign coordinator, provider adapters, new signing authority, database privilege escalation, backup-format change, cloud topology promise, live deployment, or broker purge. Preserve existing exact OCI/source/signature/age/complete-ledger checks and immutable target DB identity.

No automatic recovery claim based on exit status alone. Prefer durable refusal and an explicit operator recovery runbook over building a new automatic rollback coordinator. Post-effect failures retain rollback copies and block normal launches until an operator completes a separately verified recovery. Successful destructive restore remains recoverable through the existing app quarantine acknowledgement plus an explicit host resume step.

## Ordered implementation

### A. Durable host and task admission

- Add a BOUND active-database `restore-blocked` state to the existing host marker enum. It admits only the existing management role. It always carries an exact OperationIdentity; parsing rejects missing identity. Older images refuse its unknown state. Do not misuse candidate INTENT/sibling semantics.
- Keep host_marker.py <=300 lines (currently 298): enum entry plus reuse/delegate small state predicates, new policy parsing helper if needed rather than unrelated refactor. Keep existing marker states and their exact role matrix unchanged, including quarantine backend-only.
- Add a narrow helper module using HostMarkerTransition, existing root ownership checks, capability invalidation, atomic fsync writes and operation lock. It may begin an in-place operation only from bound NORMAL/ACK_NORMAL with verified live target identity and expected pointer generation; save previous marker privately. It may advance only the same bound operation to quarantine after full success. Explicit host acknowledgement uses a fixed root maintenance query to verify DB identity, recovery NORMAL, active restore and acknowledgement record, successful terminal operation ledger, and current exact environment/topology facts before ACK_NORMAL; never accepts an app-provided marker file.
- Register root operation phases with existing RunLedger using a distinct in-place phase name. Its database-restore phase has candidate-sibling semantics and must not be silently reused. No new generic orchestration framework or broad root command dispatcher.
- Default TenantGateTask must read an existing DeploymentRecoveryState row freshly before tenant resolution, even for existing source-gate exemptions/internal participants. Only NORMAL proceeds; missing/unreadable/non-normal refuses before task effects. Do not use .load() if it creates a default NORMAL singleton. Recovery control continues through fixed management calls, not background tasks. Preserve existing per-tenant locks and not-restored checks.

### B. Fail-closed restore lifecycle

- Reorganize only necessary existing shell lifecycle into small bounded helpers; preserve existing transport, full/historical preflight and diff approval.
- Acquire and retain the one host operation lock through import preparation, restore, and terminal state. No release/exec gap. Do not transfer a lock FD to long-lived services.
- Preflight remains before effects; then quiesce DB, durably write operation record/restore-blocked marker, stop backend/worker/beat with the currently valid old topology and prove stop success before env or SQL effects. Existing external scheduler mode must remain stopped or fail admission; do not pretend image stop controls external cron.
- Capture required pre-restore SQL, root marker, exact old env/topology and source verified input in a private root-owned operation directory before destructive effects. App-readable immutable bundle/control copies stay separate from root authority records; do not chown the authority records to uid10001.
- Once the blocked marker is installed, all exceptions/interruptions keep normal writers stopped and leave the marker plus phase evidence intact. EXIT must not call unconditional NORMAL, blindly restore old keys, delete recovery copies, or infer rollback from SQL/grant success. The existing destructive-started resume path must refuse with exact retained evidence/manual recovery instructions rather than repeating unverified destructive effects then restarting writers.
- backup_control fail records FAILED/error while retaining recovery mode and active operation. Any normal release must be reached through the explicitly checked successful completion path, not the error verb. Remove ignored errors from proofs. Pre-block harmless failures may exit without touching original marker/runtime/env.
- Successful non-reset rollback may restore NORMAL/ACK_NORMAL only after existing DB/object validation plus bound identity/environment/topology and terminal host phase facts. Successful disaster/reset writes DB QUARANTINED while still management-only blocked, then root marker QUARANTINED_AFTER_CUTOVER; start backend only. The existing recovered-superadmin acknowledgement changes DB state; workers/beat remain refused until explicit host resume verifies it and commits ACK_NORMAL. Quarantine API acknowledgement alone cannot launch processes.
- Manual recovery docs must distinguish untouched old env, transitioned new env, SQL-started and partial object restore. Old env/topology are restored only after a complete independently verified target database + object rollback under the blocked gate. An unsuccessful SQL rollback leaves the new or uncertain env untouched, runtime blocked, copies retained; explain how an operator can restore coherent old snapshot/objects/identity using fixed maintenance transport and then verify before unblocking. Do not provide an unsafe one-command 'force normal'. If no bounded verification proof is implemented, automatic host unblocking after failure is intentionally unavailable and must be reported as such.

### C. Admitted different-key import configuration transition

- Existing static signed import preflight under OLD coherent runtime uses externally pinned source verify key and prospective continuity mapping. Before any env change, register archive/intent under OLD env using explicit verified prospective admission through a narrow internal path; maintain principal eligibility, exact bundle hash/manifest/source checks and storage probe. No import flag may bypass cryptographic/source verification. Legacy service callers remain strict installed-env by default.
- Stop old runtime using validated OLD topology. Retain lock and restore-blocked gate from B. All following app calls are one-shot management processes; never run normal backend/workers with source keys over target SQL.
- Build merged env privately using the existing exact continuity allowlist plus the target-owned task generation below. Never import source storage credentials, database pointer, source verification/private signing key, host paths, scheduler controls, or general env values. Compare both old and proposed config facts to the exact committed compose family (none/build/tls/build-tls/saas/build-saas), with unchanged compose byte hashes, pointer and scheduler mode.
- Reuse host_topology_record.configuration_facts/write_topology_record to install exact validated new env and its corresponding trusted records under the existing root lock. Persist OLD/NEW byte hashes and phase before each replace; fsync private authority records/files/parents. A crash between env and record replacements must remain blocked; recovery recognizes only recorded old/new combinations and completes/refuses deterministically. Never run setup refresh to bless arbitrary drift or skip wrapper validation. Update all existing applicable records only after each was verified against old facts; no fabricated records for uninstalled layers.
- Run actual installed-env compatibility again before SQL effects. Retain fixed target identity restore before entrypoint and control rehydrate. Extend full_restore_identity admission only for same exact blocked operation with bound target identity; no general missing-row adoption.
- On any transition or restore failure, keep blocked and retain old/new config and rollback inputs. No automatic old env restore after SQL has begun. Before SQL began, a narrowly verified phase can restore exact old bytes+records without declaring whole restore NORMAL; keep blocked until reviewed recovery. Different-key success reaches quarantine only with DB/source continuity/env/object state coherent.

### D. Smallest stale-task isolation

- Introduce one target-owned non-secret optional `SPACEWORKS_TASK_GENERATION` UUID. When absent, preserve existing queue name `celery` for upgrade compatibility. During any destructive database replacement, generate a new value before runtime stops being blocked; persist it in the same trusted env/topology transition. It is EXCLUDED from archive source-continuity policy and never imported from archive.
- Configure Celery default queue/exchange/routing key consistently from this value in a tiny settings helper imported by settings.py (accepted settings-size exception). No arbitrary route registry, broker management API, queue deletion, or data model. Confirm no existing tasks publish explicit competing queue names; verify retries remain on current queue. Compose forwards value to every backend/worker/beat and scheduler topology that can produce/consume tasks. If a supported topology cannot guarantee all producers share this generation, fail restore admission before effects.
- Newly started backend and workers consume only the new queue; old target queued/unacked/ETA messages remain in the old queue and cannot match restored row IDs. Preserve old broker data for operator inspection. Do not claim old work is migrated or automatically replayed. Document that pending source-domain work/outboxes need reviewed reconciliation/re-enqueue and existing periodic schedules resume normally. Do not broaden this into guaranteed exactly-once delivery or a broker migration framework.
