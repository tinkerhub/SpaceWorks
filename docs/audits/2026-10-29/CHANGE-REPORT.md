## How request status works

The following behavior is implemented in this batch. The verification rows distinguish passing
checks, retained failures, final review and owner QA.

| Situation | Status access |
| --- | --- |
| Check-in hosting, member accounts off | Confirm an eligible upstream name to submit. No SpaceWorks account or 2FA is required. Keep the returned private link; My requests stores shortcuts for this browser and makerspace. A blank name field never automatically displays a previous visitor's service request. |
| After upstream checkout or a roster outage | Existing private status links still work without another roster lookup. New submissions still require a readable, eligible roster match. |
| Shared browser | Saved links stay hidden until explicitly revealed. Forget one or all to remove local shortcuts; this does not cancel the server request or revoke its private link. Storage failures show a warning while the current returned link remains available. |
| Different browser or cleared storage | Open the private link saved elsewhere. A typed name, email, phone or roster ID cannot recover private history. |
| Signed-in personal account | The account Requests tab lists that account's hardware and machine requests in this makerspace, even without an active community membership. Machine history uses member ownership, excluding a staff creator's legacy attribution. Check-in submissions remain separate walk-in identities. |
| Partial approval or return | Requested, approved, handed-out and returned amounts are shown separately for each request item. These quantities do not expose hidden inventory stock counts. |
| Hardware cancelled before handover | Authorized review staff cancel with a protected reason; the reservation is released once. The requester sees Cancelled, without the private staff reason. Issued requests use return/accountability workflows. |
| Machine work | Requested → Accepted → In progress → Ready to collect → Collected. Rejected and Failed are distinct terminal states. A staff reprint creates a separate accepted request and private reference; an old link continues to describe its original request. Account history includes owned children. |
| Notifications | Staff inbox and configured Telegram alerts follow the committed lifecycle. Explicit channel opt-outs and room scopes remain effective. Delivery failures do not turn an accepted transaction into a failed request; live provider delivery still requires deployment verification. |
