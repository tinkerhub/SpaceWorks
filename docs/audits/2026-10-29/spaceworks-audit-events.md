## Confirmed defects

### D-EF01 — Certificates can activate after their event is cancelled (P1 integrity)

- Source: `backend/apps/events/services_lifecycle.py:65-67` cancellation selects only ACTIVE certificates for revocation. PENDING, FAILED and RENDERING remain unchanged. `services_certificates._claim_render` at approximately135-154 checks only ATTENDED registration, not the locked Event status. `_activate` at159-183 again locks the event but ignores its status before activating the artifact. Both staff/member download views call `download_url` without an event-status filter; `member_history.registrations_for_space` deliberately retains cancellation history.
- Reproducer: an ended PUBLISHED event with an ATTENDED member has submitted certificate-enabled feedback, creating a PENDING certificate. Cancel the event, then request that certificate's download. The service can render and return a newly ACTIVE certificate even though cancellation is explicitly intended to revoke event certificates. Variant: pause rendering after `_claim_render`, cancel the event, resume `_activate`; the same outcome occurs.
- Minimal fix: recheck the **locked event status** in both claim and activation; cancelled/draft events cannot render or activate, independently of registration attendance. Preserve event→registration→certificate lock ordering. Ensure rejected activation does not charge storage or emit `event.certificate_rendered`; cleanup/failure state must remain retry-safe. Prevent staff reissue from creating a new live certificate for a cancelled event as well. Whether cancellation marks pending/failed certificates revoked or retains a non-renderable state is an explicit state-machine choice; current model permits only ACTIVE→REVOKED, so do not bypass model transitions directly.
- Tests: pending certificate after cancellation; in-flight render cancellation; failed retry after cancellation; staff reissue on cancelled event; ordinary completed/published attended event still renders; active cancellation remains revoked410. Assert no active artifact/storage charge/rendered audit for rejected cases. Neighboring tests `tests/events/test_postevent_feedback.py::test_pending_certificate_cannot_render_after_attendance_is_corrected` and `::test_mark_attended_writes_history_and_correction_revokes_certificate` cover attendance correction, not event cancellation.

### D-EF02 — Series template updates bypass occurrence capacity and approval rules (P1 data integrity)

- Source: `backend/apps/events/services_series.py:185-195` `_apply_template` copies fields directly into each occurrence and calls `event.save`; `update_series` invokes it at238-240. `Event.save` does not call the event workflow's validation. By contrast `events/services.py:update_event` rejects capacity below REGISTERED+ATTENDED occupancy, promotes FIFO waiters on a valid capacity increase, and rejects approval-policy changes after draft.
- Reproducer: publish a series, register two attendees for a future occurrence, then patch the series `capacity` to1. The series and occurrence update successfully, leaving occupancy2/capacity1. With a full occurrence plus waiter, raising series capacity does not promote the waiter. Patching `registration_requires_approval` also changes already-PUBLISHED occurrences despite the per-event draft-only rule.
- Minimal fix: have inherited template changes use the canonical occurrence update boundary (or an explicitly shared invariant helper), while preserving `series_override_fields` and aggregate transaction rollback. A viable narrow design is deriving the non-overridden field list and calling `services.update_event(..., inherit_fields=fields)` so fields remain inherited and existing checks/promotions run; avoid mutating the event before calling the service. Pass actor through `_apply_template`. Keep series→occurrence→makerspace lock order and bounded notification behavior. Reject the entire series mutation if any affected occurrence cannot adopt the template.
- Tests: series capacity reduction below occupancy409 leaves series and every occurrence unchanged; increase promotes FIFO exactly once; unlimited capacity promotes eligible waiters; approval-required occurrences never auto-promote; published approval-policy change denied; draft policy change allowed; explicit occurrence capacity/approval overrides preserved; concurrent registration versus template update never oversubscribes. Existing `tests/events/test_event_series.py::test_occurrence_override_survives_template_update_and_can_be_reset` covers title inheritance only, while `test_services.py::test_capacity_edits_promote_fifo_and_conflicts_roll_back` and `test_registration_policy.py::test_approval_policy_changes_only_while_draft` cover only direct occurrence edits.

### D-EF03 — A killed certificate render leaves an unrecoverable RENDERING state (P2 operational)

- Source: `services_certificates._claim_render` commits RENDERING before PDF/S3 work; subsequent rendering occurs outside that atomic block. `download_url` at73-82 never attempts render for RENDERING; `_claim_render` at149-150 rejects it. `EventAttendanceCertificate` has no claim timestamp/lease/token or recovery task. `revoke` accepts ACTIVE only; `reissue` refuses any non-REVOKED certificate. Normal `Exception` handling changes failures to FAILED, but process termination/restart bypasses that handler.
- Reproducer: terminate the serving process after `_claim_render` commits and before `_activate`/`_fail_render`. Subsequent downloads remain409 indefinitely and staff cannot recover through normal APIs.
- Minimal fix: use a bounded, reclaimable render claim with age and claim identity so a stale worker cannot activate another worker's claim; or provide an audited safe recovery operation that resolves expired claims. Preserve immutable PDF storage, single active certificate/revision, exactly-once quota charging and cancellation/attendance checks. Do not simply allow every RENDERING row to restart concurrently. A timestamp/token model change requires chaining from the actual events migration leaf and updating appropriate export/classification drift contracts.
- Tests: simulated process loss/stale claim recovers; live claim still409; old worker cannot activate replacement claim; repeated retries charge once; cancellation/attendance correction during recovery rejects activation. This is source-confirmed availability behavior; no destructive process termination was performed.

## Scope notes

- Event registration is independent of live presence; check-in is a separate append-only attendance act. No suggestion to conflate these states.
- Cancellation/refund provider policy was not inferred. Registration cancellation invokes the existing cancellation/payment seam; host-event cancellation retains registration rows by design. The payments track should verify the intended pending-charge/refund handling rather than imposing a new policy from this audit.
- Receipt routing remains on Payment/payment_via provenance, while attendance/history uses registered_via; this report preserves that split.
- No live payment, message, attendee check-in, PIN rotation, feed issue/revoke or certificate rendering was performed. All findings are source-confirmed and need the parent's reproducers and runtime evidence.
- No repository edits.
