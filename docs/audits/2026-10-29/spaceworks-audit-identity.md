## Confirmed actionable findings

### A-F01 — a completed sign-out can be undone by an in-flight refresh (P1)

- Source: `frontend/src/lib/apiSession.ts:85-114`, especially 101-107; `logout()` at 129-141. The existing sign-out latch is written only for unsuccessful logout. A confirmed successful logout clears the token but leaves no fence against a refresh that started earlier.
- Deterministic deferred-promise reproducer for `apiSession.test.ts`: set token `old`; start `refreshAccessToken()` with its fetch unresolved; call `logout()` and resolve its fetch with 204; assert token empty; then resolve the first fetch with 200 JSON `{access:"resurrected"}`; await refresh. Current result is `true` and token `resurrected`, despite the completed sign-out.
- Cookie boundary: if refresh server processing completed before logout but its network response is delivered last, `Set-Cookie` can also replace the logout's cleared HttpOnly cookie. JavaScript cannot directly discard that cookie. The local signed-out latch must therefore remain effective after successful logout too, across reload and same-origin tenant switching, until explicit sign-in.
- A second ordering needs coverage: old refresh -> logout -> explicit new sign-in -> old refresh response. Clearing the latch at new sign-in alone allows the old response to overwrite the new account/session. Capture an auth generation/epoch when starting refresh and refuse to apply stale results after logout or explicit sign-in; do not make refresh completion itself advance the explicit-sign-in epoch.
- Local token/latch should be updated **at sign-out initiation**, so a hanging logout request does not leave local auth usable indefinitely.
- Existing coverage gap: `frontend/src/lib/apiSession.test.ts` tests ordinary successful logout, failure/network latch and fresh-sign-in reset, but no deferred refresh versus logout or later login ordering. Backend `tests/test_auth.py::test_logout_clears_cookie_and_blocks_reuse` only covers serial requests.
- Minimal fix: account-wide persistent sign-out latch for every logout plus session-epoch guard for asynchronous refresh results. Preserve deduplication and explicit login clearing. Test success/failure, reload latch, deferred `response.json()`, explicit new login, and simultaneous refresh callers.

### A-F02 — binary downloads bypass the shared authentication recovery path (P2)

- Source: `frontend/src/lib/apiRequests.ts:203-216` (`downloadStaffFile`) and 95-106 (`tenantPublicRequestBlob`). Both use direct `fetch`, unlike `staffRequestBlob`, `memberRequestBlob`, and JSON `tenantPublicRequest`.
- Concrete staff trigger: remain signed in until the 15-minute access token expires while refresh cookie is valid, then download inventory CSV/XLSX, ledger export, procurement export, report export or QR batch ZIP. First download request returns 401 and the helper throws `Download failed (401)` without attempting refresh. A normal API request in the same session recovers correctly.
- Affected consumers: `features/staff/panels/Inventory.tsx:169`, `Ledger.tsx:115`, `ProcurementPanel.tsx:134`, `OperationsReports.tsx:129`, `QrToolsBatch.tsx:20`.
- Public-calendar trigger: `features/inventory/PublicEventsPage.tsx:49` calls `tenantPublicRequestBlob`; an expired bearer token causes JWT authentication to reject an otherwise public calendar endpoint before `AllowAny` can serve it. JSON tenant requests recover through refresh and, when appropriate, anonymous fallback; blob requests do neither.
- Deterministic tests: stale-token first GET401 -> refresh200 -> retry blob200; assert credential choice, one refresh and correct downloaded bytes. For public calendar also cover unrecoverable stale token -> clear token -> anonymous retry; preserve genuine403/404 failures, explicit tenant publishable key and no recursive retry. For staff, failed renewal should emit auth-expired event and never download an error body as a file.
- Minimal fix: reuse the existing authenticated fetch path for staff download; give public JSON/blob calls one equivalent refresh/fallback rule. Do not fix by extending token lifetime or removing authentication.

### A-F03 — organization invitation success links a member session into a staff-only console (P2)

- Source: `frontend/src/features/organizations/OrganizationInvitationRedeemPage.tsx:32-40` explicitly logs in with `surface:"member"`; redemption does not reissue tokens. Lines81-85 advertise `Open organizations` at `/admin/organizations` immediately after success.
- Backend boundary: `accounts/authentication.py::_member_surface_path_allowed` rejects `/api/v1/admin/organizations/`; organization list/detail views in `organizations/views_admin.py` are staff endpoints. `useStaffSession.ts:90-106` restores the member refresh cookie and hydrates `/auth/me` without converting that session to staff.
- End-to-end reproducer: signed-out recipient with an ordinary existing account opens a fresh organization invitation; signs in on that page; redemption succeeds; clicks Open organizations; console queries receive403 because the JWT remains a member session. Staff credentials/grants are valid after redemption, but a fresh staff sign-in is necessary and not surfaced by the success path.
- Existing automated evidence: `tests/organizations/test_governance_invitations.py::test_governance_only_account_can_open_central_staff_session` proves an explicit `surface:"staff"` login can mint `staff_api`; `test_redeem_is_single_use_and_creates_exact_authority_projection` covers redemption separately. There is no test for the frontend handoff joining those steps.
- Minimal safe fix: provide an explicit staff re-authentication handoff after redemption, preserving the member/staff token boundary. Do not silently promote an arbitrary member token. Ensure a password or configured staff social route is available according to platform switches. Also catch a failed initial `fetchMe()` in the restore promise (line46-49) so restoration failure does not become an unhandled rejection.

### A-F04 — current invariant documentation says OIDC browser sign-in does not exist (P3, docs)

- `docs/INVARIANTS.md:948-950` says the backend accepts an ID token only and no frontend renders configured OIDC providers. The real PKCE browser flow exists in `accounts/views_oidc_browser.py`, `oidc_browser_attempts.py`, `oidc_browser_http.py`, `oidc_browser_resolution.py` and frontend social UI.

## Candidate / evidence gap, not confirmed defect

**C01: cached tenant revisits versus the implicit member publishable key.** `apiSession.cacheTenantPublishableKey()` updates the default `activeTenantSlug` only when bootstrap executes; `tenantPublicRequest(slug)` using a cached explicit key does not update it. A cached A -> B -> cached A route sequence may leave implicit `memberRequest()` carrying B's public key until A bootstrap refetches. Backend target scoping should deny rather than disclose. Reproduce with HMAC/publishable enforcement and fresh TanStack bootstrap caches before filing as a functional defect. Explicit-slug JSON/blob requests themselves choose their own key correctly. A logout latch is origin-wide by design and should not be keyed to a tenant, since the refresh cookie/account session is shared on that origin.

## Explicit limitations and intentional exceptions

- All runtime results and provider-adapter failure tests still require the parent ledger; no real Google/Apple/OIDC/SMS/email service was exercised here. Native attestation/provider configurations may be dormant; their deterministic tests and runtime availability switches, not a live credential call, are the evidence.
- Break-glass `/control/` password login when platform passwords are disabled but no admin SSO exists is documented intentional behavior, not a bypass finding.
- The one-release missing-surface JWT compatibility shim grants only member authority and is deliberate; no request to remove it is inferred.
- Password changes revoke browser refresh tokens and native grants. Ordinary browser access JWTs remain short-lived (15minutes); this review does not reinterpret that existing contract as an immediate bearer-revocation defect.
- Organization grants never confer local role identity or machine-type management. Retired Guest Admin/Print Manager enum fallback is migration compatibility, not an active feature to restore.
- Payment settlement, event operational flows, physical handover, archive/restore execution and external deployment scripts are owned by sibling audit domains; this report maps their identity/authorization entry boundaries only.

## Follow-on review of the first A implementation (2026-10-29)

The initial epoch fix in apiSession prevents an old refresh from setting a token after a newer login. Its API callers still had a companion race: staffFetch waits for that old refresh, receives false because of the epoch mismatch, then unconditionally calls expireStaffAuthSession, clearing the new login. tenantPublicRequestWithRetry likewise unconditionally clears the new token before anonymous fallback. The same hazard exists when the initial or retried request's 401 arrives after explicit login.

Deferred regression: old token/request ->401; hold refresh response; explicit setAccessToken(new-login); release refresh200(old-token); await old request; new-login must remain and no auth-expired listener should fire. Also test new login before initial401 and before retry401, for staff JSON/blob and tenant JSON/blob paths.

Minimal companion fix: expose read-only session generation; capture at request start; before every 401 recovery, after refresh, and before every clear/expire/retry, require generation unchanged. Internal refresh must retain generation. If changed, reject the stale request using its original/last response without retrying the old operation using the new account. String comparison is weaker than generation because logout/relogin can reuse a string. Parent notified; no frontend files edited by this subagent.
