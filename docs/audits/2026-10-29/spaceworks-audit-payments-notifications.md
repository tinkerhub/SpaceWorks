## Confirmed source findings

### D-F01 P1: Stripe amount conversion overcharges zero-decimal currencies

`backend/apps/payments/models_settings.py:9` accepts every lowercase three-letter currency. Payments hold major units as Decimal(12,2). Raw Checkout `services.py:199`, generic provider Checkout `services.py:250`, native PaymentIntent `services_mobile.py:120`, and application fee calculation `services.py:273` multiply every currency by 100.

Reproduction: configure `jpy`, create a 10.00 JPY charge, generate Stripe Checkout or mobile intent. Payload contains 1000, which Stripe interprets as 1000 JPY. Currency settings accept this configuration, so the configured major-unit amount is multiplied by 100 at the provider boundary.

Primary external verification: https://docs.stripe.com/currencies — Stripe API amounts use currency minor units; 10 USD is 1000 and 10 JPY is 10. Stripe has special cases: ISK and UGX require its legacy two-decimal representation, while HUF/TWD charge and payout conventions differ. Do not blindly apply an ISO zero-decimal list. Razorpay semantics were not independently checked in this pass; the generic seam's unconditional multiplication is evidenced, but the confirmed overcharge statement concerns Stripe.

Minimal fix: central provider-aware conversion used by Checkout, mobile intent and fee calculation; validate unsupported precision instead of truncating it, or explicitly reject unsupported currencies before provider calls. Preserve USD/INR behavior. Existing terminal financial rows must not be silently rewritten. Pending fee values already calculated under a different conversion need a deliberate compatibility policy.

Regression gap: `payments/test_payment_settings_validation.py::test_api_rejects_malformed_default_currency` only checks syntax; `payments/test_razorpay_provider.py::test_checkout_sends_integer_minor_units_and_an_uppercase_currency` uses INR; `payments/test_mobile_payments.py::test_connect_payment_intent_uses_direct_charge_account_and_fee` uses a two-decimal currency. Add JPY whole amount, fractional JPY refusal, ordinary two-decimal positive control, Stripe special-case currency, and Connect fee/native parity.

### D-F02 P2: Daily managed email cap can be bypassed through retry/outbox

`backend/apps/integrations/dispatch.py:121-134` persists quota-denied messages as FAILED with text/html bodies, without incrementing/reserving the daily counter. `integrations/services.py:13-40::retry_email_log` accepts every FAILED stored-body message and enqueues it without quota accounting. `integrations/management/commands/flush_email_outbox.py` uses that retry path, and delivery itself does not reserve quota.

Reproduction: managed tenant with email cap 0, dispatch normal persisted tenant email, then retry from Email Log or run the outbox flush. The failed cap row becomes pending and sends without consuming quota. Cap 1 likewise permits subsequent capped messages through retry. This also occurs automatically through the operator outbox recovery path.

Minimal fix: distinguish quota-denied/unreserved messages from provider-failed/already-reserved messages. A retry of the former must reserve quota under the existing locked daily counter or remain ineligible; ordinary transport retries must not double-charge. Define next-day recovery explicitly rather than leaving the counter bypass in place. Retain immutable audit/history and existing retry authorization.

Regression gap: `tests/test_email_async.py::test_retry_endpoint_reenqueues_failed_log`, `::test_retry_endpoint_reclaims_stale_sending_and_rejects_fresh`, and `tests/test_email_module_gating.py::test_a_skipped_email_cannot_be_retried` cover retry status and modules, but not cap-denied retry. Add manual and flush cap 0/1 refusal/no-provider-call/no-counter-overrun, next-day policy, normal provider retry once-reserved control.

### D-F03 P2: Queued room notifications ignore destination deactivation or scope withdrawal

`backend/apps/integrations/dispatch_channels.py::dispatch_channel` resolves active matching destinations at enqueue and stores NotificationScope in payload. `_deliver_notification:226-270` rechecks the channel module and deleted destination, but not `destination.is_active` or current destination scope. It calls Telegram/webhook with the live destination even after an operator disables or narrows it.

Reproduction: enqueue a scoped machine notification for an active Slack/Telegram/Discord destination; deactivate the room or change its machine/type/category scope to exclude the subject before the worker runs; delivery or retry still posts to that destination. Disabling a destination therefore only governs new dispatches.

Minimal fix: delivery-time active/scope recheck against persisted subject scope. Return a terminal skipped reason on withdrawal; never fall back to a legacy/global room. Preserve active matching room and no-room legacy behavior. Destination channel changes are already forbidden by serializer and are not a finding.

Regression gap: `tests/test_notification_destinations.py::test_deleting_a_room_keeps_its_delivery_history_and_stops_queued_sends` covers deletion; `::test_a_deactivated_sole_room_does_not_fall_back_to_the_legacy_webhook` covers fresh dispatch only; `tests/test_notification_channel_modules_p10.py::test_a_queued_row_is_skipped_when_the_module_goes_away_mid_flight` covers module withdrawal. Add queued deactivation, scope narrowing, retry-after-withdrawal and matching active control.
