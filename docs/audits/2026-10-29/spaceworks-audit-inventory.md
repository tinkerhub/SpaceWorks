## Confirmed source findings requiring reproduction/regressions

### B-F01 — Individual inventory can acquire phantom counts through stocktake (P1)

- `backend/apps/operations/services_stocktake_workflow.py:97-99` accepts `product_id` for either tracking mode, computes expected aggregate quantity and creates an ordinary product line.
- `backend/apps/operations/services_stocktake_helpers.py:40-52` revalidates tenant/container/asset identity at apply but never rejects an individual product-only line. `_ledger_entries_for_line` then creates a product variance and `_apply_ledger_entries` calls `availability.apply_stocktake_delta`.
- `backend/apps/inventory/availability_quantities.py:253-284` applies that variance to aggregate buckets without creating/updating an `InventoryAsset`.
- This is reachable in the normal UI: `frontend/src/features/staff/panels/StocktakeCountSection.tsx:139` lists all products in Product mode despite carrying `tracking_mode` in its option type.
- Reproducer: individual product with one AVAILABLE asset/count; submit a product-only count line with counted_quantity=2; complete with inventory staff, approve/apply as a distinct authorized reviewer. Aggregate available/total become2 while only one physical unit row exists. It recreates the user's original “available but cannot accept” inconsistency. Aggregate and asset lines can also both be recorded for the same product.
- Minimal fix: reject individual product-only count lines in creation **and in apply-time validation** for retained/legacy approved lines; require exact asset counting. UI filters Product mode to quantity items or moves a selected individual product to Asset mode. Keep asset-backed `apply_stocktake_delta` primitive available to legitimate stocktake ledger operations.
- Needed regressions: API400 and unchanged line/stock/audit; legacy approved individual product-only line refused atomically; quantity product counts and real individual asset counts continue working; product+asset mixing cannot bypass it.
- Existing adjacent coverage: `tests/test_stocktake_integrity.py::test_stocktake_rejects_issued_asset_count_before_line_create`, `::test_stocktake_apply_rejects_stale_product_expected_quantity`, `::test_stocktake_apply_rejects_asset_that_became_unstocktakeable_after_count` — none assert the product-only individual path.

### B-F02 — Invalid/stale/foreign operation payload IDs escape as500 (P2)

Bounded to these client-supplied references, not all model lookups:

| API entry | Raw lookup | Trigger |
|---|---|---|
| `POST /admin/makerspace/{id}/stock-transfers` | `operations/services_shared.py:7` `_container` | `source_container_id` or `destination_container_id` names a deleted/nonexistent or other-tenant container |
| same, intra-space | `operations/services_transfers.py:81-84,103-106` `_apply_intra_makerspace_line` | `asset_id` or `product_id` is missing/foreign |
| same, cross-space | `operations/services_transfers.py:150-153` `_apply_cross_makerspace_line` | source `product_id` is missing/foreign |
| `POST /admin/makerspace/{id}/stocktakes` | `services_stocktake_workflow.create_stocktake` → `_container` | `container_id` missing/foreign |
| `POST /admin/stocktakes/{id}/count-lines` | `services_stocktake_workflow.py:89,92,97` | container/asset/product missing/foreign |
| `POST /admin/products/{pk}/assets/generate` | `operations/services_qr_assets.py:95` | `print_batch_id` missing/foreign |

The corresponding serializer fields are plain IntegerField values, not validated scoped relations. Authorized view resolution succeeds for the owning makerspace/session/product, then `.get(...)` raises model DoesNotExist. `hardware_requests/exceptions.py::workflow_exception_handler` handles DjangoValidationError and named workflow errors, **not** ObjectDoesNotExist; DRF's default handler does not translate that exception. Thus a user selecting a record concurrently deleted, or sending a foreign ID, receives an unhandled500.

Transfer and count-line mutations run under atomic blocks, so a failed later line should roll back the transfer header, earlier successful lines, adjustments/audits and stock. Asset-generation batch lookup is inside its transaction, so any tracking conversion rolls back. Those rollback expectations require assertions in new API regressions. Avoid solving this with a global ObjectDoesNotExist handler: use scoped `get_object_or_404` or explicit typed validation at these boundaries, keeping `select_for_update` where already present. Foreign IDs should remain indistinguishable from missing ones. Advertise the resulting404/400 in each affected OpenAPI response.

Adjacent coverage is `tests/test_transfer_and_container_guards.py`, `tests/test_operations_api.py`, `tests/test_stocktake_integrity.py`; they cover existing foreign-parent/product-scope checks but omit these dangling submitted references.

### B-F03 — Cross-space transfer matches against the source category's tenant-local FK (P2)

- `backend/apps/operations/services_transfers.py:162-168` filters destination inventory using `category_id=src.category_id`.
- Categories are scoped to their own makerspace (`inventory/models.py:20-53`); two legitimate corresponding categories have different PKs. Therefore a categorized source cannot match an existing properly categorized destination product.
- On no match, creation at `services_transfers.py:176-188` omits category. A second transfer of the same categorized source still looks for the source category PK, fails to match that newly created uncategorized row, and creates yet another destination product.
- Reproducer: two spaces each with their own MCU category; same-name quantity product in each category; transfer from source twice. Existing destination stock remains unchanged and extra uncategorized rows appear instead of topping up the matching destination product.
- Minimal fix must explicitly choose a destination-local semantic category match (code/slug as supported by the category contract), or define/document another deterministic matching strategy; never attach source category FK to destination. Preserve quantity-vs-individual refusal and private creation policy. Add repeat categorized-transfer tests, same-name/different-category separation and individual destination guard tests with nonnull categories.
- Existing `tests/test_operations_api.py::test_cross_makerspace_transfer_credits_existing_destination_product` and `::test_cross_makerspace_transfer_rejects_individual_destination_match` use category=None, so cannot reveal this case.

### B-F04 — Unit generation can write a withdrawn QR print-batch capability (P2)

- `POST /admin/products/{pk}/assets/generate` checks `asset_units` in its view and locked service, but accepts `print_batch_id` and `create_print_batch` without checking `qr_print_batches`.
- `operations/services_qr_assets.py:94-103` retrieves/creates a print batch and subsequent lines add items, bypassing the disabled module's ordinary batch APIs. Retained data is intentionally left in place when a module is uninstalled.
- Reproducer: enable asset_units and qr_print_batches, create a batch, disable only qr_print_batches, then generate units with that retained batch ID; it mutates the otherwise withdrawn batch surface. `create_print_batch=true` likewise creates a new batch while off.
- Minimal fix: under the existing makerspace lock, conditionally require `qr_print_batches` whenever either batch option is requested. Leave unbatched asset generation available with `asset_units` alone. Keep the same rule for `/control/` service callers. Add both-option off-state tests asserting no unit/QR/batch/stock/audit side effects, plus an unbatched success control.
- Related raw missing-batch reference is covered by B-F02. Existing happy-path coverage `tests/test_operations_api.py` uses valid enabled batches; off-state tests mainly exercise `asset_units` and normal batch API routes.
