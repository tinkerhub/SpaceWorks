## Confirmed defects

### C-F01 — Missing/stale consumable pool makes staff Start return 500 (P2)

- Entry: `POST /api/v1/admin/machine-service/requests/{id}/start`, `MachineServiceStartView` → `_MachineServiceActionView.post` → `service_workflow.start`.
- Source: `backend/apps/admin_api/serializers_machine_service.py:141-148` accepts any positive `consumable_pool_id`. `backend/apps/machines/service_workflow_actions.py:159-162` calls `MachineConsumablePool.objects.get(pk=consumable_pool_id)` without handling a missing row. `apps/hardware_requests/exceptions.py:workflow_exception_handler` does not map model `DoesNotExist`; DRF also does not map it.
- Reproducer design: accepted job on an authorized idle machine, otherwise valid start data, `consumable_pool_id` equal to an absent positive ID and `planned_grams=1` (printer also needs positive estimated minutes). The lookup throws instead of returning a documented 400/409. This can also occur when a retained client draft points at a pool deleted by administrative data management.
- Minimal fix: **inside the existing transaction and after request/machine authorization**, resolve the pool with a same-tenant `select_for_update(of=("self",))` lookup and convert absence to `ServiceConsumptionInvalid` (or a field-level DRF `ValidationError`). Keep canonical `reserve_for_request` compatibility/activity/unit checks; never introduce a global `ObjectDoesNotExist` catch. Do not look up a foreign pool before scoping it to `locked.makerspace_id`.
- Required regression cases: nonexistent ID; foreign tenant pool; same-tenant pool for another type/machine; retired pool; valid compatible pool. For all failures assert request remains accepted/unassigned, machine stays idle, zero reserve adjustments, counters unchanged and no assigned/started audit/notification. Existing `test_start_endpoint_reserves_requested_consumable_grams` and `tests/machines/test_consumable_reservation_scope.py::test_grams_reservation_accepts_the_machine_type_pool_and_rejects_another_type` cover successful reservation/type rejection, but not this missing-ID API boundary. Scope-first test should prove foreign request/unauthorized actor is denied before pool selection.

### C-F02 — Reprint creation bypasses managed creation limits and locked module check (P2)

- Entry: `POST /api/v1/admin/machine-service/requests/{id}/reprint` → `service_workflow_followups.create_reprint`.
- Source: `backend/apps/machines/service_workflow_followups.py:33-50` checks the PII fence and terminal status, then directly creates an accepted child. Unlike `service_workflow_actions.submit`, it calls neither `limits.check_quota` for `machine_service_open` / `machine_service_submit` nor the locked module check. `makerspaces/limits_usage.py:126-151` explicitly counts these child rows in open and daily usage.
- Impact: a managed space already at either cap can create unlimited accepted reprint jobs, despite the documented creation-service quota invariant (`docs/INVARIANTS.md:38-43`). The API's pre-service module check also cannot serialize a concurrent uninstall against creation.
- Minimal fix: take the existing PII fence then makerspace **NO KEY UPDATE** lock before locking the original request; recheck machine_service and both managed quotas with the service creation lock order (do not add a makerspace lock after request/queue locks). Preserve self-host unlimited behavior, root attachment provenance, payment reset and the intended reprint lifecycle. Determine whether the print daily quota applies to staff reprints from the existing printer policy; do not silently invent that policy.
- Required regression cases: managed open cap reached; managed daily cap reached; self-host succeeds with low configured caps; module disabled at locked creation boundary; concurrent creators serialize at last slot; rejected creation writes no child/audit. Existing `tests/test_machine_service_workflow.py::test_submit_enforces_managed_open_and_daily_caps`, `::test_submit_caps_are_dormant_on_self_host`, and `tests/test_machine_service_kernel_b2.py::test_payment_hook_reprint_provenance_and_registry_seam` cover neighboring rules but no capped reprint.

### C-F03 — Presigned POST can overwrite validated machine/service/maintenance documents (P1 integrity)

- Affected APIs: public typed/legacy printer uploads and staff service attachments; machine-document presign/finalize; maintenance-log-document presign/finalize.
- Sources:
  - `backend/apps/machines/service_storage.py:presigned_upload` POST branch (`Key=object_key`, approximately line136); `finalize_upload` non-PUT branch only returns `object_size(object_key)` (approximately line180).
  - `backend/apps/machines/storage.py:101-109` POST branch signs `Key=object_key`; `finalize_upload` at152-154 returns the final object's size for POST.
  - `backend/apps/maintenance/storage.py:107` signs final key; `finalize_upload` at150-152 does the same POST short circuit.
- Reproducer design: obtain POST policy, upload a valid file, finalize/attach it, then reuse the still-unexpired POST to upload different bytes to the same key. The DB metadata/validation/audit still describe the first upload while staff retrieve the replacement. PUT paths already use staging, so this is method-dependent. No attack was executed.
- Minimal fix: POST and PUT both issue presigns for staging only. Finalization validates/promotes to a final key that no client presign can write, and reads/cleanup/purge/accounting handle staging consistently. Preserve existing attached-file loser protection in `service_storage.finalize_file`; a retry or concurrent loser must not delete a committed winner. Keep bounded byte/MIME/signature checks and private bucket policy.
- Required regressions: captured POST params name staging key for all three storages; upload then promotion; reusing presign changes staging only and final bytes remain original; duplicate finalize winner remains intact; missing/invalid/oversize failures clean only eligible staged data; legacy final object handling is deliberate; object storage unavailable yields typed503. Existing tests validate contents and ownership but do not test POST replay after attachment. See `tests/test_machine_service_files.py::test_presign_finalize_happy_path_and_no_key_leak`, `::test_put_attach_failure_compensates_final_object`, `::test_finalize_rechecks_staged_file_owner_under_lock`; `tests/test_machines.py::test_machine_documents_presign_finalize_list_url_delete_and_reuse_guard`; `tests/maintenance/test_service_accounting.py::test_finalize_and_delete_charge_exact_validated_size`.
